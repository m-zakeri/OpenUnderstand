## 1. Testing architecture

```
tests/
├── _isolation.py            # the stub meta-path finder (single implementation)
├── conftest.py              # isolation bootstrap + shared fixtures
├── unit/                    # example-based tests (74)
│   ├── test_kind.py         #   entity & reference kinds, inverse references
│   ├── test_ref.py          #   reference objects (kind/ent/file/scope/line/col)
│   ├── test_entity_and_db.py#   parent-child, unknown entities, db queries
│   └── test_misc.py         #   accessors, dunders, null handling
├── property/                # Hypothesis property-based tests (23, bonus)
│   └── test_api_properties.py
├── generated/               # curated Pynguin output (5, Part 4)
│   └── test_api_pynguin_curated.py
└── _pynguin_support/
    └── sitecustomize.py     # stubs the parser stack for Pynguin runs
```

All three tiers test the **same** unit in isolation; they differ only in how
the inputs were chosen — hand-picked, generated by Hypothesis, or generated by
Pynguin. Select a tier with `pytest -m unit`, `-m property` or `-m generated`.

### Isolation strategy (testing in isolation)
Importing `openunderstand.oudb.api` normally drags in the entire ANTLR/javalang
Java-parsing stack (`openunderstand.ounderstand.project` is imported by nearly
every metric module). That machinery is irrelevant to the database-backed
api/db layer and makes "unit" tests slow and brittle.

`tests/_isolation.py` provides a PEP 302 meta-path finder that synthesises a
harmless stub for any import under four prefixes:

| Prefix | Why it is stubbed |
|---|---|
| `openunderstand.metrics` | the metric engine — needs a populated `.udb` |
| `openunderstand.ounderstand` | the parser/listener stack |
| `gen` | the absolute-import form the metric modules use for the ANTLR parsers |
| `git` | GitPython, imported by `api.py` for the out-of-scope `update_db()` only — and required for Pynguin to run at all (see §6) |

It is installed **before** the api is imported, decoupling the unit under test
from its heavy collaborators. Every test then runs against a fresh **in-memory
SQLite** database (peewee `:memory:`), so tests are hermetic, fast, and
order-independent.

Two callers share that one implementation:

| Caller | Why it needs the shim |
|---|---|
| `tests/conftest.py` | the pytest suite |
| `tests/_pynguin_support/sitecustomize.py` | Pynguin runs in a separate process **and** venv, so it cannot import a conftest; it loads `_isolation.py` by path |

> Note: the stub covers the **bare** `gen` prefix only; `openunderstand.gen.*`
> is deliberately not stubbed, so the real generated parsers remain importable
> if ever needed.
>
> The stub's module-level `__getattr__` refuses to synthesise dunder names.
> Introspection tools walk `sys.modules` probing `__file__`, `__all__` and
> friends, and expect either a real value or `AttributeError`; handing them a
> class makes them fail confusingly (Hypothesis' constant-collection pass
> crashes with `TypeError: argument of type 'type' is not iterable`).

### Fixtures (in `conftest.py`)
| Fixture | Purpose |
|---|---|
| `db` | fresh in-memory SQLite bound to all models |
| `kinds` | entity + reference kinds, with inverse (`_inv`) wiring |
| `entities` | `File → Class → Method → Parameter` tree |
| `references` | a `Java Call` reference |
| `open_db` | an `api.Db` wired to the in-memory database |
| `make_kind` / `make_ent` / `make_ref` | wrap a model row as an api dataclass |

## 2. Environment setup (Part 1)

**Requires Python 3.10, 3.11 or 3.12** (any of the three — CI tests all of them).
Check with `python --version`; if `python` is not on your PATH on Windows, use
`py` instead.

Windows (PowerShell), four commands from the repo root:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements-dev.txt
```

Linux/macOS: same, but `source .venv/bin/activate` for step 2.

> If PowerShell refuses to run `Activate.ps1` (execution policy), either run
> `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` first, or skip
> activation entirely and call the interpreter directly — every command below
> also works as `.\.venv\Scripts\python -m <command>`
> (e.g. `.\.venv\Scripts\python -m pytest tests -q`).

Optional: `pre-commit install` to mirror the CI lint gate on every commit.

## 5. CI/CD (Part 2)

`.github/workflows/ci.yml` runs on pushes to `feature/**`, `master`, `main`
and on PRs:

1. **lint** — `ruff check tests` (zero-error gate), plus a non-blocking
   `mypy tests` step
2. **test** — install deps, run pytest with branch coverage on Python
   3.10/3.11/3.12, then enforce the coverage gates from `coverage.json`
3. **reports/artifacts** — JUnit XML, Cobertura `coverage.xml`, `coverage.json`
   and the HTML report are uploaded as build artifacts; optional Codecov upload
4. **mutation** — opt-in job (manual `workflow_dispatch`) runs mutmut on Linux

Reproducibility: `requirements-dev.txt` bounds every tool both below **and
above**, so a new upstream major release cannot turn a green build red without a
code change. The lint job installs from that same file rather than doing a bare
`pip install ruff`, which was the one remaining unpinned tool. Add pip caching
and `PYTHONHASHSEED=0` (deterministic set/dict iteration — `Db.ents()` returns a
set) and the pipeline is reproducible across the whole matrix.

## 6. Automated test generation — Pynguin (Part 4)

Pynguin lives in its **own** venv (it pins old dependencies that conflict with
the tools in `requirements-dev.txt`):

```powershell
python -m venv .venv-pynguin
.\.venv-pynguin\Scripts\Activate.ps1
pip install "pynguin>=0.43.0" -r requirements.txt
.\scripts\run_pynguin.ps1     # or ./scripts/run_pynguin.sh on Linux/macOS
```

The scripts use a **30 s** search budget (`--maximum-search-time 30`), which is
what the committed results were produced with; the whole run takes about a
minute including start-up, and writes to `tests/generated/`. **Deactivate
`.venv-pynguin` and reactivate `.venv` before running anything else.**

See `tests/generated/README.md` for the curate→evaluate→refactor→integrate
workflow, and `docs/REPORT.md` §4 for the results.

> **Three start-up failures had to be fixed to get this running** — all three
> are configuration, not tool defects:
>
> 1. `RecursionError` — `dill` recursively pickles the peewee ORM graph.
>    Fixed by `sys.setrecursionlimit(30000)` in the Pynguin shim.
> 2. `NameError: name 'IterableClassWatcher' is not defined` — **this symbol
>    belongs to GitPython, not Pynguin.** `dill` reconstructs GitPython's
>    deprecated `Iterable` class, whose metaclass refers to its own name as a
>    module global that is unbound during reconstruction. `api.py` imports `git`
>    only for the out-of-scope `update_db()`, so `git` was added to the
>    isolation shim's stubbed prefixes and the problem disappeared.
> 3. `ModuleNotFoundError: No module named '_ou_test_isolation'` — the shim
>    loaded `tests/_isolation.py` under a synthetic module name without
>    registering it, and Pynguin re-imports the `__module__` of everything it
>    reaches in order to parse its syntax tree. Fixed by adding the module to
>    `sys.modules` before `exec_module`.

Latest run: **14 raw cases generated**, curated down to **5**. Coverage delta
over the manual suite: **0 %** (see `docs/REPORT.md` §4.2 for the measurement).

## 7. Mutation testing (Part 5)

**mutmut has no native Windows support**
([issue #397](https://github.com/boxed/mutmut/issues/397)), so on Windows use the
**Cosmic Ray** engine (configured in `cosmic-ray.toml`). Both engines are already
installed by `requirements-dev.txt`; no extra install step is needed.

One command, from the repo root with `.venv` activated:

```powershell
.\scripts\run_mutation.ps1
```

That wrapper is equivalent to:

```powershell
cosmic-ray init cosmic-ray.toml cr-session.sqlite
cosmic-ray exec cosmic-ray.toml cr-session.sqlite    # runs the suite per mutant; be patient
cr-report cr-session.sqlite
```

On **Linux, macOS or WSL** you can use mutmut instead — `./scripts/run_mutation.sh`,
equivalent to:

```bash
mutmut run
mutmut results
mutmut export-cicd-stats     # machine-readable summary
```

> mutmut 3.x (what `requirements-dev.txt` pins) removed the `html` and
> `junitxml` subcommands that 2.x had. Use `mutmut browse` for an interactive
> report and `mutmut show <id>` for a single mutant's diff. `setup.cfg`
> likewise uses the 3.x configuration keys (`source_paths`,
> `pytest_add_cli_args_test_selection`).

Mutation score = `killed / total` (equivalently `killed / (killed + survived)`).

Recorded run (Cosmic Ray, whole-module `api.py`, session in `cr-session.sqlite`):
**839 mutants, 104 killed, 735 survived → 12.40 %**.

That headline figure is a *whole-file* score and is dominated by mutants planted
in code the unit suite deliberately does not execute. Restricting it to the
lines the suite actually covers — a join of `cr-session.sqlite` against
`coverage.json` — gives the representative number:

| Scope | Mutants | Killed | Survived | Score |
|---|---|---|---|---|
| Whole file (`api.py`) | 839 | 104 | 735 | 12.40 % |
| **In-scope (covered lines)** | **100** | **75** | **25** | **75.00 %** |
| Out-of-scope | 739 | 29 | 710 | 3.92 % |

> **Scope note — read before quoting these numbers.**
> `cr-session.sqlite` is the *baseline* run, taken **before** the five targeted
> tests described in `docs/REPORT.md` §5.2 were added. Each of those five
> mutants was afterwards re-applied by hand and confirmed to fail the suite, so
> the in-scope figure is now **80 killed / 100 → 80.00 %**; the committed
> session file still shows the 75 % baseline because regenerating it means
> re-running all 839 mutants (**≈ 90 min**).
>
> To refresh it: `.\scripts\run_mutation.ps1` — then re-run the split below.

Reproduce that split with:

```powershell
python -c "import json,sqlite3;cov=json.load(open('coverage.json'));k=next(f for f in cov['files'] if f.endswith('api.py'));ex=set(cov['files'][k]['executed_lines']);c=sqlite3.connect('cr-session.sqlite');r=[(l,o) for l,o in c.execute('select s.start_pos_row,w.test_outcome from mutation_specs s join work_results w on s.job_id=w.job_id')];i=[o for l,o in r if l in ex];print('in-scope',len(i),'killed',i.count('KILLED'),round(i.count('KILLED')/len(i)*100,2),'%')"
```

See `docs/REPORT.md` §5.2 for the analysis of surviving mutants and the tests
added to kill them.
